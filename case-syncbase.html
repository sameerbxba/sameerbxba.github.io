SyncBase, and what happened when I audited my own tool

I built a tool to find where teams are working from contradicting assumptions, then wrote a NIST AI RMF assessment of it. Checking the document against my own source code is where it got interesting.

ContextSelf-directed
My roleDesign, build, assessment
When2026
Built withReact, Anthropic API, Vercel
01  /  The situation

Building something in order to have something to govern

SyncBase started as a way to test my own thinking about where generative AI really fits into day-to-day work. It reads across a project's documents and flags where teams are working from contradicting assumptions, the kind of mismatch that turns into rework three weeks later.

The second half of the project turned out to matter more than the first. Once it existed, I wrote a full NIST AI Risk Management Framework assessment of it, which meant assessing my own system with nobody to hide behind. That's a different exercise from writing about somebody else's.

02  /  The governance decision

Precision over recall, and stating what it costs

The model was the easy part. The hard part was deciding which of a long list of flags were the few worth showing.

I set the system to surface deliberately fewer conflicts than it could. A tool that flags everything gets ignored on day two, and an ignored tool has a worse risk profile than no tool, because people believe it's watching.

Why this was a governance decision

Choosing precision over recall means accepting that the system will miss real conflicts. The assessment says so in those words, and says what the choice costs. A risk document that only records the upside of a decision is a marketing document with a table in it.

The other decision I'd defend: the assessment separates the one feature that really uses a model from the rule-based one. Governing string concatenation as though it were a model is how these documents lose credibility with anyone who reads them properly.

03  /  What I got wrong

Three things, and I only found them by checking

A control I'd documented as implemented didn't exist

I verified the assessment against my own source code instead of my memory of what I'd built, and found a control marked as implemented that I'd never written. The document and the system had diverged, and the document was the confident one.

The scanner doesn't work on the deployed site

The model call is made from the browser, which works locally and fails once the application is deployed, because the credential can't be shipped to the client. The live site therefore returns pre-computed results for the sample projects and an error for anything a user creates. For a while the assessment didn't say so.

The document contained a quotation I couldn't source

A quote and an attribution went into an early draft that I couldn't stand behind on a second read. Both were removed.

What I changed as a result

The assessment now carries a deployment limitation section that names the hosting problem directly, a verification section stating what was checked against the code and what wasn't, and a change log recording every correction including the removed quote.

A governance document that was never wrong usually means nobody checked. The change log is the part of that document I'd point to first.

04  /  What changed as a result

The habit, more than the document

The concrete outputs were a corrected assessment, a set of fixes to the tool, and a disclosure on the live site about what does and doesn't work.

What stuck was a habit: check the document against the running system instead of trusting my memory of building it. That's what I carried into the next project, and it's what caught a much more serious defect there, where a control was recording human decisions that no human had made.

It also changed how I read other people's documents. The first thing I now look for is whether anything in them has ever been corrected.

05  /  What's still open

Better said here than found by someone else

  • The scanner still isn't live. The fix is to move the model call behind a serverless function so the credential stays on the server. It's disclosed on the site but still open.
  • Accuracy has never been measured. No claim about how often the tool is right appears anywhere, because nothing has been measured, and I'd rather have a gap than a number I can't support.
  • The assessment is a self-assessment. Nobody independent has reviewed either the tool or the document, and the document says so. It's a management assertion, not an audit, and calling it anything else would be exactly the kind of overstatement it exists to avoid.

The assessment covers intended use, out-of-scope uses, risk tolerances, a model card, monitoring thresholds and decommission criteria, and carries a change log of everything I corrected.
